# Code Structure Documentation

This repository is a small Conan and CMake build orchestration tool. It provides
one place to define repeatable build actions, exposes those actions through a
command-line interface and a Tkinter GUI, and keeps each action's generated
files in a separate directory under `build/`.

The repository contains two related projects:

1. The **build menu framework**, implemented primarily in `conanfile.py` and
   `build_helper/`.
2. A **sample C++ project**, under `example/`, used to demonstrate the framework
   and verify the build, test, coverage, and analysis flows.

The maintained source is the root configuration, Python helpers, profiles,
environment definitions, documentation, and `example/` tree. Most of the
contents of `build/` are generated by Conan, CMake, Ninja, tests, and analysis
tools and should not be treated as source code.

## Repository Map

```text
.
|-- CMakeLists.txt                 Root CMake project
|-- configurations.cmake           Platform and feature definitions
|-- conanfile.py                   Conan recipe and build-menu entry point
|-- CMakeUserPresets.json          Includes generated Conan CMake presets
|-- GCC.cmake                      Optional compiler/toolchain settings
|-- .environment/
|   |-- conda_env.yaml              Reproducible tool list
|   `-- conda-lock.*.yml            Platform-specific lock files
|-- activate_conda_env.bat          Windows environment bootstrap
|-- activate_conda_env.sh           Unix environment bootstrap
|-- linux_build_runner.sh           Unix GUI convenience launcher
|-- build_profiles/                 INI files describing build actions
|-- build_helper/
|   |-- build_helper.py             Conan subprocess orchestration
|   |-- coverage.py                 gcovr and clang-tidy command builders
|   |-- package_helper.py           Per-profile output directory creation
|   `-- gui/interface.py             Tkinter profile and process monitor
|-- example/
|   |-- CMakeLists.txt              Application target and dependencies
|   |-- main.cpp                    Sample executable entry point
|   `-- Calculator/
|       |-- CMakeLists.txt          Library and optional test targets
|       |-- include/Calculator/     Public library header
|       |-- src/                    Library implementation
|       `-- test/                   GoogleTest sources
|-- 02_Documentation/               User and maintainer documentation
`-- .github/workflows/              Packaging and release workflows
```

The `build/` directory is intentionally ignored by Git. A typical configured
build contains a profile directory such as `build/Unit_Tests/Debug/`, with
Ninja files, `compile_commands.json`, Conan-generated dependency files, object
files, executables, test results, and coverage data.

## Main Entry Point: `conanfile.py`

`conanfile.py` has two responsibilities that cooperate but should be kept
conceptually separate.

### `ProjectConan`

`ProjectConan` is the Conan recipe consumed by commands such as:

```text
conan build . --profile=<generated-profile> --build=missing
```

Its responsibilities are:

- Declare package identity (`project`, version `1.0.0`) and supported Conan
  settings (`os`, `compiler`, `build_type`, and `arch`).
- Declare the runtime/build dependency `fmt/11.1.4` in `requirements()`.
- Add `gtest/1.15.0` as a test requirement when the custom Conan
  configuration `user.project:unit_test` is enabled.
- Place Conan's CMake build folder below `build/<configuration>`. The
  configuration is read from `user.project:build_target_path`.
- Generate a `CMakeToolchain` and `CMakeDeps` integration. The toolchain
  receives the CMake variable `UNIT_TEST`, which controls test target creation
  in the CMake files.
- Configure and build with CMake. When unit testing is enabled, it also runs
  CTest through `cmake.test()`.
- Run `cmake.install()` during packaging. The current example has no install
  rules, so this is infrastructure for future package contents rather than a
  complete package definition today.

### `BuildMenu`

`BuildMenu` is the application-level dispatcher. It discovers profiles in
`build_profiles/`, accepts a selected profile from either the CLI or GUI, and
routes the profile's `action` to `BuildHelper`.

The CLI is created at the bottom of the file. Every `.ini` file becomes an
option, for example:

```text
python conanfile.py --Debug_Build
python conanfile.py --Unit_Tests
python conanfile.py --gui
```

The `execute()` sequence is:

1. Select a profile and read `build_profiles/<name>.ini` with
   `configparser`.
2. Create `BuildHelper` and validate that only the supported sections and keys
   are present.
3. Flatten the profile values into a `SimpleNamespace`, so values are
   available as `options.action`, `options.build_type`, and so on.
4. Read `depends_on` and recursively execute any prerequisite profile whose
   output directory does not yet exist.
5. Dispatch the action:
   - `build` -> `BuildHelper.build()`
   - `unit_test` -> `BuildHelper.build_test()`
   - `coverage_analysis` -> `BuildHelper.coverage_analysis()`
   - `static_code_analysis` -> `BuildHelper.static_code_analysis()`
   - `get_dependencies` -> print the action name; Conan dependency retrieval
     occurs when a later Conan build uses `--build=missing`
6. Construct `Package_Helper`, which ensures `build/<selected-profile>/`
   exists.

The CLI path does not create a GUI object. `BuildHelper` therefore catches the
missing GUI callbacks when it tries to register process monitoring. In GUI mode
the same subprocesses are registered and polled by the Tkinter event loop.

## Build Profiles

Profiles are INI files with two allowed sections.

### `[settings]`

These values are copied into a temporary Conan profile at
`build/.profiles/<profile>.conanprofile`:

```ini
[settings]
arch=x86_64
build_type=Debug
compiler=gcc
compiler.cppstd=gnu20
compiler.libcxx=libstdc++11
compiler.version=16
os=Windows
```

The allowed keys are `arch`, `build_type`, `compiler`, `compiler.cppstd`,
`compiler.libcxx`, `compiler.version`, and `os`. `BuildHelper` warns when the
profile OS differs from the running platform and replaces the OS value with
the actual platform while writing the generated Conan profile.

### `[execution]`

The allowed keys are `action` and `depends_on`.

`action` selects a method in `BuildHelper`. `depends_on` is a comma-separated
list of profile names that must be run first. The dependency check is based on
whether `build/<dependency>` exists, so the directory itself is used as the
completion marker.

The profiles currently represent this intended workflow:

| Profile                | Action                 | Intended role                                                           |
| ---------------------- | ---------------------- | ----------------------------------------------------------------------- |
| `Get_Dependencies`     | `get_dependencies`     | Named prerequisite for dependency setup; it does not itself call Conan. |
| `Unit_Tests`           | `unit_test`            | Build with tests and coverage instrumentation, then run CTest.          |
| `Debug_Build`          | `build`                | Build the application without enabling test targets.                    |
| `Coverage_analysis`    | `coverage_analysis`    | Convert unit-test coverage data into HTML and XML reports.              |
| `Static_Code_Analysis` | `static_code_analysis` | Run clang-tidy using the unit-test compilation database.                |

`Debug_Build` explicitly depends on `Get_Dependencies` and `Unit_Tests`, which
means selecting it can build the test configuration before the normal debug
configuration. The coverage and static-analysis profiles are intended to use
the `Unit_Tests` output, because that output supplies coverage files and
`compile_commands.json`.

### Profile dependency caveat

The dependency values in `Coverage_analysis.ini` and
`Static_Code_Analysis.ini` currently include `Get_Dependencies.ini`, while the
dispatcher normally expects a profile stem such as `Get_Dependencies`. Since
the dispatcher appends `.ini` when loading a profile, those two values can
produce an invalid filename if those profiles are selected. Profile dependency
values should use the stem form consistently.

## `BuildHelper`: Translating Profiles into Commands

`build_helper/build_helper.py` owns the operational build logic.

### Normal build

`build(configuration)` performs these steps:

1. Delete `build/<configuration>/` to guarantee a clean configuration.
2. Write a temporary Conan profile from the selected INI settings.
3. Build a `conan build` command with:
   - the repository root as the Conan project,
   - the generated profile,
   - `--build=missing`,
   - `user.project:build_target_path=<configuration>`, and
   - platform-specific compiler configuration.
4. Start Conan with `subprocess.Popen`.
5. Register the process with the GUI when a GUI is active.

`build_test(configuration)` follows the same path but additionally passes
`user.project:unit_test=True`. That value travels through `ProjectConan.generate()`
into the CMake cache as `UNIT_TEST=1`.

### Platform toolchain configuration

`__conan_toolchain_conf()` requires `CONDA_PREFIX`, so builds are expected to
run inside the project Conda environment.

- On Windows, it selects the Conda MinGW executables
  `x86_64-w64-mingw32-gcc`, `g++`, `ar`, and `ranlib`. It verifies that the
  MinGW sysroot contains `crt2.o`, then adds startup and linker paths.
- On Unix, it selects `gcc` and `g++` from the environment's `bin` directory.
- Both platforms request the Ninja CMake generator and pass compiler executable
  mappings to Conan's CMake toolchain.

The separate `GCC.cmake` file expresses a similar compiler selection directly
for CMake. The active Python build path currently supplies its compiler values
through Conan configuration instead of explicitly loading `GCC.cmake`.

### Coverage and static analysis

Both analysis methods clean their own result directory but consume the existing
unit-test build at `build/Unit_Tests/Debug/`.

`coverage_analysis()` calls `coverage_command()` from `coverage.py`. That
function:

- Requires at least one `.gcda` file from the unit-test build.
- Locates `gcovr` and the platform-appropriate gcov executable.
- Excludes environment, build, test, and Conan cache paths.
- Writes detailed HTML output to
  `build/Coverage_analysis/coverage.html`.
- Writes XML output to `build/Coverage_analysis/coverage.xml`.

`static_code_analysis()` calls `code_quality_analysis()` and:

- Requires `build/Unit_Tests/Debug/compile_commands.json`.
- Removes test source entries from the clang-tidy input list.
- Uses clang-tidy checks covering diagnostics, bug-prone code, performance,
  portability, analyzer, CERT, C++ Core Guidelines, modernize, and readability
  rules.
- Adds strict compiler warning arguments and promotes selected warnings to
  errors.
- Exports fixes to `build/Static_Code_Analysis/clang-tidy-fixes.yaml` and
  mirrors process output to `clang-tidy.log`.

## CMake Layer

### Root `CMakeLists.txt`

The root project:

1. Requires CMake 3.25 and declares the C++ project `BuildExample`.
2. Enables CTest only when the `UNIT_TEST` cache variable is true.
3. Sets C++20 and exports `compile_commands.json`.
4. Includes `configurations.cmake`.
5. Adds the `example/` subdirectory.
6. Prints the selected build type and directory compile definitions during
   configuration.

### `configurations.cmake`

This file converts platform and feature state into preprocessor definitions:

- `OS_WINDOWS=1` on Windows, otherwise `0`.
- `OS_LINUX=1` on Unix/Linux, otherwise `0`.
- `UNIT_TEST=1` when supplied by Conan for a test build, otherwise `0`.

These definitions are directory-level compile definitions and are therefore
available to targets below the root directory.

### Example target graph

```text
BuildExample (executable)
|-- Calculator_lib (static library)
|   `-- example/Calculator/src/example_calculator.cpp
|-- fmt::fmt (Conan dependency)
`-- main.cpp

When UNIT_TEST=1:

Calculator_tests (executable)
|-- test/test_example_calculator.cpp
|-- Calculator_lib
`-- GTest::gtest_main (Conan test dependency)
```

`example/CMakeLists.txt` adds the Calculator subdirectory, finds `fmt` through
Conan-generated CMakeDeps files, creates the `BuildExample` executable, and
links it to `Calculator_lib` and `fmt::fmt`.

`example/Calculator/CMakeLists.txt` creates the static library from the public
header and implementation, and exposes `include/` as a public include path.
When `UNIT_TEST` is enabled it also finds GTest, creates `Calculator_tests`,
links it to the library and `GTest::gtest_main`, and registers it with CTest.

For GNU builds, both the library and test executable receive `--coverage`.
The library also links the `gcov` interface. Running the tests then produces
the `.gcda` files consumed by `gcovr`.

The sample C++ code is intentionally small: `Calculator::add()` accumulates a
`uint8_t` value, and `main.cpp` demonstrates both the Calculator header and the
Conan-provided `fmt` library.

## GUI Layer

`build_helper/gui/interface.py` defines `BuildGUI`, a Tkinter application that:

- discovers every `.ini` profile in `build_profiles/`,
- displays profiles and their status in a two-column tree view,
- exposes an `EXECUTE` menu command wired to `BuildMenu.execute`, and
- polls registered subprocesses every 100 to 250 milliseconds, showing
  `Starting`, `Running`, `Finished`, or `Failed`.

The GUI does not implement build behavior itself. It is a presentation layer
over the same `BuildMenu.execute()` path used by the CLI. The process monitor
tracks subprocess completion; build output remains owned by the child process
or the logging helper.

## Environment Bootstrap

`.environment/conda_env.yaml` defines the toolchain from conda-forge:

- Python 3.14 or newer and Conan,
- GCC/G++ 16 and supporting runtime/binutils packages,
- CMake and Ninja,
- gcovr for coverage, and
- clang-tools for static analysis.

The Windows and Unix activation scripts perform the same broad lifecycle:

1. Check that Conda and the environment definition exist.
2. Hash `conda_env.yaml`.
3. Generate a platform-specific lock file when the lock file is missing or the
   YAML hash changed.
4. Remove and recreate `.environment/envs/conda_env` when the lock or
   environment is stale.
5. Activate the environment by prefix and verify activation.

The Windows script uses PowerShell for SHA-256 and `conda.bat`; the Unix script
uses `sha256sum` and sources Conda's shell integration. `linux_build_runner.sh`
is a convenience wrapper that activates the environment and starts
`python conanfile.py --gui`.

## Generated Files and Output Layout

The important generated locations are:

```text
build/
|-- .profiles/                       Temporary Conan profiles
|-- Debug_Build/Debug/               Normal debug Conan/CMake build
|-- Unit_Tests/Debug/                Test build, CTest data, compile database
|-- Coverage_analysis/               coverage.html and coverage.xml
`-- Static_Code_Analysis/            clang-tidy log and exported fixes
```

Conan normally creates a nested `Debug/` build directory because
`cmake_layout()` is used. Its `generators/` directory contains the generated
toolchain and dependency files, including `conan_toolchain.cmake`, fmt config
files, and (when applicable) GTest config files.

`CMakeUserPresets.json` includes generated `CMakePresets.json` files from the
Debug and Unit_Tests generator directories. These references are useful after
the corresponding profiles have been configured, but they depend on generated
files and are not an independent build definition.

`package_helper.py` currently only creates the selected profile's top-level
output directory. It does not copy binaries or assemble a distributable
archive.

## CI and Packaging

The workflows under `.github/workflows/` are packaging/release scaffolding:

- `package.yaml` archives the repository contents on a published release and
  uploads the zip as an artifact.
- `release.yaml` runs on version tags, attempts to run `./build.sh`, zips the
  `build/` directory, and attaches it to a GitHub release.

There is currently no `build.sh` in the repository, so the tag-based release
workflow requires correction before it can perform its build step. This is
separate from the local `conanfile.py` build flow.

## How to Extend the Project

### Add a Conan dependency

Add the package to `ProjectConan.requirements()` in `conanfile.py`, then find it
from CMake with `find_package()` and link its imported target from the relevant
`CMakeLists.txt`.

### Add a profile

Create a new INI file in `build_profiles/` with valid `[settings]` and
`[execution]` entries. The CLI discovers it automatically, and the GUI lists it
automatically. Use dependency stems without `.ini` and ensure any analysis
profile depends on the build output it consumes.

### Add a new action

1. Add the action name to a profile.
2. Add a matching branch in `BuildMenu.execute()`.
3. Implement the operation in `BuildHelper` or a focused helper module.
4. Decide which generated output directory marks completion.
5. Add a focused test or executable verification for the new command.

### Add a C++ target

Add a CMake target in the appropriate subdirectory, keep its include and link
requirements explicit, and register tests with `add_test()` when they are
controlled by `UNIT_TEST`.

## Current Design Limits

The project describes itself as a beta build tool, and the code reflects that
status. In particular:

- Build directories are cleaned before normal, test, coverage, and analysis
  actions, so incremental reuse is not implemented.
- The dependency completion test is directory existence, not a recorded
  success state. A failed or partial action can leave a directory behind.
- `Get_Dependencies` is a profile-level convention, not a dedicated Conan
  install command.
- Package creation is only partially implemented; the Conan recipe has an
  install hook but the sample CMake project has no install rules.
- The GUI process monitor reports completion but does not provide cancellation
  or detailed error handling.
- The repository has a sample C++ unit test, but no automated unit-test suite
  for the Python build-menu framework itself.
- The release workflow's `build.sh` reference is not backed by a tracked file.

These limits are useful context when adapting the repository: the framework is
intended as a configurable starting point, while the example project is the
reference implementation of how a consuming CMake project is connected.
